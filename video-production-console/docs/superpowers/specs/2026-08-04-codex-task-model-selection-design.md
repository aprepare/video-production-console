# Codex 任务模型选择设计

日期：2026-08-04  
状态：待用户审核  
目标系统：`video-production-console`

## 1. 背景与目标

当前控制台启动 Codex CLI 任务时，没有显式传入模型与推理强度，因此所有选题、二创、口播和混剪任务都会继承本机 Codex 全局配置。目前实际继承的是：

- 模型：`gpt-5.6-sol`
- 推理强度：`medium`
- Provider：`custom`

这会造成三个问题：

1. 用户无法在控制台看出某个任务实际使用了什么模型。
2. 不同类型任务无法按成本、速度和质量临时选择模型。
3. 修改全局 Codex 配置后，历史任务和续聊任务的执行环境不再清晰。

本次改造的目标是：

- 在设置页维护控制台默认模型与默认推理强度。
- 每次发起任务时允许临时覆盖默认值。
- 每个任务持久化实际解析后的模型配置。
- 继续同一 Codex 任务时，严格沿用该任务首次执行时的模型配置。
- 在任务详情中明确显示实际模型和推理强度。

默认配置保持为 `gpt-5.6-sol + medium`。

## 2. 范围

### 2.1 本次包含

- 设置页的默认模型与默认推理强度。
- 选题工作台发送消息时的任务级临时覆盖。
- 正式项目中选题、二创、口播和混剪任务的任务级临时覆盖。
- 后端 API、领域模型、数据库、Codex CLI 命令构造与任务详情的适配。
- 历史数据库兼容。
- 设置、API、命令构造、续聊语义和前端交互测试。

### 2.2 本次不包含

- 不在网页中维护 Provider、Base URL 或 Codex 登录凭据。
- 不自动探测远端 Provider 当前支持的全部模型。
- 不根据余额或任务类型自动切换模型。
- 不允许运行中的任务更换模型。
- 不修改全局 `~/.codex/config.toml`。
- 不改变现有最多 4 个 Codex 任务并发的调度语义。

## 3. 方案比较

### 3.1 方案 A：只修改全局 Codex 配置

每次用户选择模型后，由控制台改写全局配置，再启动 CLI。

不采用。并发任务之间会互相覆盖；桌面端和 CLI 也会受到控制台写入的影响，无法保证单任务可追溯性。

### 3.2 方案 B：只把选择值放入命令快照

任务启动时把模型放进现有 `config_snapshot_json`，不增加数据库字段。

不采用。当前运行器会在任务启动阶段覆盖该快照；该字段更适合记录完整命令快照，不适合作为任务模型的唯一权威来源，也不利于查询和历史兼容。

### 3.3 方案 C：设置默认值 + 任务独立字段 + CLI 显式参数

采用此方案。控制台先解析默认值和任务覆盖值，把最终值写入任务独立字段，再显式传给 Codex CLI。命令快照继续记录最终命令，但不承担权威存储职责。

优点：

- 并发任务互不影响。
- 历史任务可追溯。
- 续聊语义稳定。
- 不修改桌面端或全局 Codex 配置。
- 后续可按任务类型增加推荐预设，而不改变底层契约。

## 4. 核心产品决策

1. 设置页默认值为 `gpt-5.6-sol` 和 `medium`。
2. 新任务界面默认显示“继承默认值”，同时把当前解析结果展示为只读提示，例如“实际将使用：gpt-5.6-sol · medium”。
3. 用户可以只覆盖模型、只覆盖推理强度，或同时覆盖两者。
4. 后端在创建任务时立即把最终解析值写入任务记录；之后即使设置页默认值变化，已创建任务也不变化。
5. 同一任务的继续执行不再次询问模型，始终沿用原任务值。
6. 新建另一项任务时重新应用最新默认值。
7. 任务详情显示实际模型与推理强度；命令预览中也可看到已脱敏的 CLI 参数。
8. 前端选项只是便捷输入，后端校验才是安全边界。

## 5. 设置契约

### 5.1 `PublicSettings` 新增字段

```json
{
  "codex_default_model": "gpt-5.6-sol",
  "codex_default_reasoning_effort": "medium"
}
```

这两个字段属于非密钥公开设置，可以通过现有设置 API 读取和更新。

### 5.2 默认值

当数据库尚无配置、迁移旧版本，或配置文件中缺少字段时，服务层提供以下默认值：

```text
codex_default_model = gpt-5.6-sol
codex_default_reasoning_effort = medium
```

不得因为某次设置更新只提交了其他字段而把这两个值清空。

### 5.3 推理强度允许值

后端允许：

- `low`
- `medium`
- `high`
- `xhigh`
- `max`
- `ultra`

比较时先去除首尾空白并转为小写。空字符串不视为合法显式值；任务请求若想继承默认值，应省略字段或传 `null`。

### 5.4 模型名称校验

模型名称不能直接拼接成任意 CLI 参数。统一校验规则：

- 去除首尾空白后长度为 1—128 个字符。
- 只允许 ASCII 字母、数字、点、下划线、短横线、冒号和斜杠。
- 不允许内部空白。
- 不允许以 `-` 开头，避免被解析成额外 CLI 参数。
- 不允许控制字符、引号、反引号或 shell 元字符。

建议正则：

```regex
^[A-Za-z0-9_./:][A-Za-z0-9_.:/-]{0,127}$
```

模型是否真实存在由 Codex CLI 和 Provider 在执行时判断。控制台只负责格式安全，不维护可能过期的硬编码模型白名单。

## 6. 任务数据模型与数据库

### 6.1 `codex_tasks` 新增字段

```text
model_name       TEXT NOT NULL DEFAULT 'gpt-5.6-sol'
reasoning_effort TEXT NOT NULL DEFAULT 'medium'
```

领域模型 `CodexTask`、存储层扫描和写入逻辑同步增加：

```go
ModelName       string
ReasoningEffort string
```

### 6.2 迁移策略

新增幂等数据库迁移：

1. 检查字段是否存在。
2. 为旧表增加字段。
3. 将历史空值补为 `gpt-5.6-sol` 和 `medium`。
4. 新任务始终显式写入解析后的最终值。

历史任务无法可靠还原当时实际继承的全局配置，因此使用本次升级时已知的现行默认值作为兼容标记。任务详情可直接显示该值，不额外制造“未知”状态。

### 6.3 权威来源

- `model_name` 和 `reasoning_effort` 是任务运行与续聊的权威来源。
- `config_snapshot_json` 记录命令和环境快照，仅用于审计、排障和界面展示。
- 设置页默认值只在“创建新任务”时参与解析。

## 7. API 设计

### 7.1 新任务请求

项目任务创建 API 和选题消息 API 增加两个可选字段：

```json
{
  "model": "gpt-5.6-sol",
  "reasoning_effort": "medium"
}
```

解析顺序：

```text
请求显式覆盖值
→ 若缺失则读取控制台默认设置
→ 统一规范化和校验
→ 把最终值写入 codex_tasks
→ 入队执行
```

只覆盖其中一个字段时，另一个字段继承默认设置。

### 7.2 续聊请求

续聊 API 不接受新的模型配置；即使客户端误传，也不用于覆盖任务记录。服务端从原任务读取 `model_name` 和 `reasoning_effort` 构造恢复命令。

这样可以确保同一个 Codex session 不会因为前端状态或设置更新而隐式换模型。

### 7.3 `taskView` 响应

任务详情增加：

```json
{
  "model": "gpt-5.6-sol",
  "reasoning_effort": "medium"
}
```

列表页可以选择只展示模型简称，详情页必须同时显示两项。

### 7.4 错误响应

以下情况在任务创建前返回 HTTP 400，不产生任务记录：

- 模型名为空、过长或包含非法字符。
- 推理强度不在允许集合内。
- 设置页提交非法默认值。

如果格式合法但 Provider 不支持该模型，任务正常创建并进入执行；CLI 的失败事件和错误日志按现有实时反馈链路展示，不静默回退到其他模型。

## 8. Codex CLI 命令

### 8.1 首次执行

`BuildExecCommand` 在现有参数基础上加入：

```text
-m <model_name>
-c model_reasoning_effort="<reasoning_effort>"
```

示意：

```text
codex exec -m gpt-5.6-sol -c model_reasoning_effort="medium" ...
```

实现时使用参数数组传给 `exec.CommandContext`，不得拼成 shell 字符串执行。命令预览也必须由参数数组安全格式化，不反向参与执行。

### 8.2 继续执行

`BuildResumeCommand` 使用原任务持久化字段：

```text
codex exec resume <session_id> -m <原任务模型> -c model_reasoning_effort="<原任务强度>" ...
```

具体参数顺序以当前 CLI 已验证的命令构造方式为准，但测试必须断言首次执行和恢复执行都包含同一组模型参数。

### 8.3 日志与脱敏

模型名和推理强度不是密钥，可以出现在任务详情和命令预览中。Provider 密钥、环境变量值和其他密钥仍不得进入 Prompt、manifest、数据库明文日志或网页响应。

## 9. 前端交互

### 9.1 设置页

Codex 配置区新增：

- 默认模型：可编辑文本框，初始为 `gpt-5.6-sol`。
- 默认推理强度：下拉框，初始为 `medium`。
- 简短说明：默认值只影响之后新建的任务，不修改运行中任务，也不改写本机全局 Codex 配置。

保存后重新获取设置并展示服务端最终值，防止局部更新导致界面与数据库不一致。

### 9.2 新任务配置

在以下发送入口复用同一个轻量“任务配置”组件：

- 选题工作台发送消息。
- 项目内启动选题、二创、口播和混剪任务。

组件包含：

- 模型：`继承默认值（gpt-5.6-sol）` 或自定义模型。
- 推理强度：`继承默认值（medium）` 或允许值下拉项。
- 解析结果：`实际将使用：<model> · <effort>`。

默认保持折叠，减少对日常操作的干扰；用户展开后可以临时覆盖。发送成功后，表单恢复为继承默认值，不把上一次临时覆盖误带到下一项新任务。

### 9.3 续聊交互

继续同一任务时不显示可编辑模型控件，只显示：

```text
继续使用：gpt-5.6-sol · medium
```

如果用户需要换模型，应新建任务，而不是修改正在续聊的任务。

### 9.4 任务详情

任务详情元信息增加：

- 实际模型。
- 推理强度。
- 首次执行或继续执行标记。

这两项与现有 Prompt、CLI 命令、实时事件、问题、回答和最终结果放在同一个详情上下文中，方便排查“发了什么、用什么跑、返回了什么”。

## 10. 状态、并发与失败语义

- 模型选择不改变任务状态机。
- 并发调度仍由现有 1—4 的控制台并发设置负责。
- 排队中的任务已经冻结模型配置；设置页更新不会改变队列内任务。
- CLI 报模型不可用、Provider 余额不足或鉴权失败时，任务进入现有失败状态并保留完整事件。
- 控制台不得在失败后自动切换模型重试，以免产生不可预期成本和结果差异。
- 用户可根据失败原因，用新模型重新新建任务。

## 11. 测试设计

按测试驱动方式实现，先写失败测试，再补最小实现。

### 11.1 设置层

- 缺少新字段时返回默认值。
- 保存合法模型和各允许推理强度。
- 拒绝空模型、非法字符、前导短横线和超长模型名。
- 拒绝非法推理强度。
- 局部更新其他设置不会清空模型默认值。

### 11.2 存储与迁移

- 新数据库包含两个新字段。
- 旧数据库升级后历史任务有兼容值。
- 创建、读取、列表和任务详情均保留实际模型配置。

### 11.3 HTTP API

- 请求未传覆盖值时使用设置默认值。
- 只覆盖模型时，推理强度继承默认值。
- 只覆盖推理强度时，模型继承默认值。
- 同时覆盖时保存两项覆盖值。
- 非法输入返回 400 且不创建任务。
- 选题消息和正式项目任务行为一致。
- `taskView` 返回实际模型配置。

### 11.4 CLI 命令

- `BuildExecCommand` 含 `-m` 和 `model_reasoning_effort`。
- `BuildResumeCommand` 使用原任务字段。
- 修改全局默认值后，恢复旧任务的命令不变化。
- 参数以独立 argv 传递，不存在模型名命令注入。

### 11.5 前端

- 设置页正确显示、校验并保存默认值。
- 新任务默认继承设置。
- 临时覆盖被发送到 API。
- 发送完成后临时覆盖重置。
- 续聊只显示原任务配置，不允许修改。
- 任务详情显示实际模型和推理强度。

### 11.6 回归验证

- 运行 Go 全量测试。
- 运行前端单元测试与构建。
- 用构造命令或假 CLI 验证参数，不启动微信视频号，不启动剪映，不产生真实混剪任务。
- 重启控制台后验证设置和任务字段仍能读取。

## 12. 实施边界与完成标准

完成必须同时满足：

1. 设置页能保存并恢复默认模型和推理强度。
2. 选题、二创、口播和混剪的新任务都能继承或覆盖默认值。
3. 每个任务数据库记录包含实际模型和推理强度。
4. 首次执行命令显式传入模型参数。
5. 续聊命令沿用原任务参数。
6. 任务详情能看到实际配置。
7. 非法输入在启动 CLI 前被拒绝。
8. 不修改全局 Codex 配置，不泄露密钥，不影响现有 1—4 并发设置。
9. 相关后端与前端测试通过。

## 13. 后续可选增强

以下内容不纳入本次实现：

- 按任务类型提供“快速 / 均衡 / 高质量”预设。
- 从 Provider 动态拉取可用模型列表。
- 显示模型调用成本和 token 统计。
- 根据余额或错误类型建议重新运行的模型。
- 管理员配置允许模型白名单。

这些增强都可以复用本次建立的任务级模型契约，无需再次修改任务续聊的核心语义。
